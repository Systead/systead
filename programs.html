Programs

Specialist depth without surrendering the whole House.

A Program is a deep specialist application inside Systead.

It can be powerful, opinionated, and domain-specific. It cannot become a separate kingdom that owns the operator’s general memory or bypasses Core safety.

Programs are replaceable.The House is durable.No Program owns the person.
The contract

Programs inherit foundations. They contribute specialist understanding.

This allows Systead to become broad without forcing every domain into generic tables or duplicating trust and recovery machinery inside each application.

Programs may

  • define specialist records and workflows;
  • provide domain-specific dashboards and tools;
  • contribute scoped specialist intelligence;
  • import and export domain formats;
  • request approved House context;
  • use shared commands, decisions, audit, and recovery.

Programs may not

  • redefine Systead’s identity;
  • own the operator’s general memory;
  • silently access unrelated Rooms;
  • bypass Core permissions or command review;
  • trap the House in undocumented proprietary structures;
  • remain required after their domain is removed.
Program 01

Publishing is the first proving domain—not the definition of Systead.

Publishing combines long-lived projects, many versions, canon, research, rights, production, external releases, contacts, decisions, and correction history. It is an unusually demanding test of continuity.

Current internal working name

AuthorMachine

The name identifies the present private v10 line and development discussions. It is not locked as the public release name.

What is not final

Release name, package boundaries, included features, pricing, licensing, platform support, and release identity.

What it proves

One Program can reach deep professional capability while using shared House memory, authority, provenance, recovery, and exit foundations.

Future Programs

The model is broader than publishing. The roadmap is not a fantasy catalogue.

Systead may eventually support other deep domains, but no unbuilt Program should be marketed as a product commitment.

Possible future domains could include independent business operations, research, household administration, property, casework, or other complex long-lived responsibilities. Those examples demonstrate architectural range. They are not announced products, names, release dates, or promises.

The platform should be designed so another Program can exist. It should not pretend that Program already does.
