# Program 01: Publishing

**Current internal working name:** AuthorMachine
**Public release name:** Undecided
**Public alpha label:** Publishing House
**Maturity:** Private pre-alpha / active extraction target

## Purpose

Program 01 is Systead's first deep specialist Program.

It exists to support the full operational life of books and publishing projects rather than treating a manuscript file as the whole product.

## Naming rule

Use:

- **Program 01: Publishing** for architectural and roadmap references;
- **AuthorMachine** for the existing private code line, v10 heritage, internal build, and working discussions;
- **publishing Program** for general public explanation.

Do not imply that AuthorMachine is the final release name until a naming decision is formally recorded.

Publishing House is the plain-language public label for the Program during the founding alpha. It describes the capability without replacing the architectural name or locking the final release identity.

## Founding-alpha profiles

The first configuration profiles are:

- **Publishing House** for a small press or imprint operating several books;
- **Author Studio** for a solo author managing a long-lived body of work;
- **Author-Publisher** for an operator who owns both the creative and release workflow.

Profiles configure the same Program. They are not separate products and must not fork canonical record types.

## Founding-alpha desks

The first bounded desks are:

- catalogue and project cockpit;
- manuscript and canon;
- editions and production;
- rights, metadata, and release;
- decisions, evidence, and review.

Alpha 01 is successful when these desks can share House memory, make current standing understandable, and export their records. It is not required to automate external publishing platforms.

## Why this Program comes first

Publishing pressures almost every important Systead capability:

- long-lived projects;
- source files and revisions;
- canonical standing;
- decisions and evidence;
- complex domain records;
- multiple outputs and editions;
- external publication effects;
- rights and metadata;
- contacts and commitments;
- post-release correction;
- local intelligence with high consequence for mistakes.

## Feature-status rule

A visible private feature may be:

- implemented and active;
- partially implemented;
- experimental;
- private-only;
- a design study;
- planned but not working;
- unsuitable for public release.

Public documentation must not flatten these states into one feature promise.

## Generalization rule

Before moving a private v10 capability into Program 01:

1. remove private data and machine-specific assumptions;
2. identify shared Core dependencies;
3. define records and migrations;
4. define commands and authority;
5. define import/export and removal behavior;
6. replace private fixtures with synthetic examples;
7. add tests around actual behaviour;
8. label maturity honestly.

## Relationship to Systead

Program 01 proves how deep a Systead Program can become.

It does not define the limits of the House.

The public line is:

> **One House. Many Programs. Publishing is the first.**
